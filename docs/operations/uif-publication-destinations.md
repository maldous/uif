# UIF publication and installation channels

UIF has distinct source, artifact, instruction-distribution and runtime channels.
This guide maps the seven currently identified channel kinds; it is not a live
inventory, completeness certificate, new delivery gate or publication grant.
The dated operational inventory, original receipts and concrete residuals stay
in [UIF-268](https://linear.app/maldous/issue/UIF-268). Detailed execution receipts
and private runtime observations remain in their authorized private custody,
not copied into this source guide.

## Keep the channels separate

| Known channel | Required binding and existing route | What it does not establish |
| --- | --- | --- |
| GitHub `develop` source | Owned task branch, exact source review, applicable checks and normal expected-head PR merge with canonical commit/tree/parent readback. | Installation, main/tag release, native ownership or product acceptance. |
| GitHub `main`, release records and immutable tags | Separately selected frozen candidate, existing release qualification/review, current authorized publisher and original-effect reconciliation. Follow UIF-160/127/218. | A green feature build is not release permission; an empty supported collection is not global absence. |
| Private Python wheel artifact | Exact source and physical wheel bytes/hash, packaged module checks and original build receipt. Use the selected `project_checks` build contract. | A package version or wheel is not a registry publication, signing result or deployed version. A registry destination remains separately selected. |
| Foo native Core installation | Actual installed program preimages and consumer, original operation/current custody, applicable project controls and a qualified preserving adoption path. | A source merge or invertible prepared patch does not preserve an old process's retry/claim objects or authorize a restart. |
| Environment-owned instruction bundle | Selected policy manifest/profile, actual bundle/file readback and the role's explicit instruction load. | Readable source or a startup pointer is not runtime enforcement, authentication or full product compliance. Retained older bundles are not automatically the selected policy. |
| Shared Foo `project_checks` helper | Its current deployed schema/catalog, exact branch and immutable expected commit, declared toolchain/resource/setup and original status/receipt. Cloud retains the shared helper writer. | Check/build availability does not supply a lint, publish or deploy target. Source-specific contracts remain scoped to their exact operation. |
| Private plugin source release | Exact source/package/release identity and verified source readback through its existing owner. | Package/App/release names are not installed connection IDs, effective OAuth grants or an old/successor cutover. UIF-211 retains that distinct reconciliation. |

Do not infer one channel from another or silently relabel an older artifact as
current-head qualification. Preserve actual timestamps, immutable source/output
identities and original operation receipts in the owning record. Mark unknown,
unsupported, unselected and observed values distinctly. A dated observation is
not continuous or current live attestation.

## Checks are not publication

Discover the actual supported target catalog for each consuming operation.
The dated UIF inventory records `test`, `build`, `check`, `compile` and
`environment` targets, no declared lint command and no publish target. A later
catalog change does not rewrite that historical evidence; revalidate the target
actually needed rather than replaying unrelated accepted checks.

Use [exact-branch project checks](project-checks-source-branch.md). Preserve the
original operation identity through uncertain submission/status. Use a new
reviewed source unit for a genuine correction, not a new ID to replay an uncertain
effect. Existing accepted checks may be reused only at their qualified bindings.

The [native publication metadata adapter](native-publication-handoff.md) offers
pure normalization and original-receipt binding. `catalog`, `plan` and
`bind_receipt` do not execute a native publisher, verify an artifact independently,
obtain an OAuth grant or attest current authority. Do not add that metadata
interface as a blanket release gate or manufacture a generic release route.

## Scoped remaining work

Keep concrete gaps with the existing owner and issue rather than inventing
another queue or duplicating an implementation:

- UIF-160/127/218: actual selected frozen release, consuming publisher and
  original-operation/remote outcome, including applicable rollback evidence.
- UIF-120/130/159/247: native consuming integration, real current custody and
  state-preserving adoption; source preparation is a separate completed stage.
- UIF-211: exact installed connector identities, consumer continuity and any
  separately authorized retirement or rollback.
- UIF-267/268: the selected project-specific check/publication mapping and its
  observed destination evidence, not a replacement controller or provider.

These are dependent-operation boundaries, not a universal project start hold.
Independent authorized source, documentation and deterministic work continues.
No new account, credential, storage/provider choice, persistent grant, production
publication-as-test, main/tag promotion, unpause or security change is authorized
by this map. Resolve applicable authority immediately before a real effect and
verify its terminal receipt and destination through the existing supported route.
