## Intended model

Five project roles (UIF, ANQR, OffMenu, Circular Quay and CIX) each use their own
cloud Git checkout, CPU allocation and storage independently of Foo. The general
Cloud role has no Git configuration or repository binding. Scoped authorized MCP
execution may target the correct project worktree/branch without binding Cloud
to Git. Additional Foo Codex sessions supplement these roles only after actual
allowance, prerequisites and ownership reconciliation. See the versioned local
[uif-worker-policy.md](uif-worker-policy.md), version 1.1.0.

The user's temporary alignment instruction keeps the five project agents not
runnable while reconciliation occurs; Cloud is excepted. This records requested
control state only. It is not proof that every agent was stopped or fenced, and
it does not authorize a restart when a documentation PR merges.

## Remaining mismatches and ownership

- Version 1.1 is not yet inherited from any observed develop branch. A candidate
  PR or a ready-for-review label must not be described as adopted source.
- New clones, nested agents and existing sessions must explicitly use an accepted
  checkout and its root/scoped instructions. Changes in a different branch or
  repository are not inherited automatically. Canonical Foo checkout rollout and
  actual agent acknowledgments are not verified by this source checkpoint.
- The UIF read-only white-room configuration still has null repository mappings
  for Circular Quay, CIX and ANQR at the observed develop revision. Circular Quay's
  mapping correction is separately owned by [PR 22](https://github.com/maldous/uif/pull/22).
  This documentation change does not overwrite that configuration work.
- CIX product activation restrictions and private-data publication boundaries
  remain in force. Operations repository visibility must be checked against live
  metadata; intended public visibility does not change actual access or authorize
  disclosure. No visibility setting is changed here.
- The [2026-11-10 rollout record](rollout-2026-11-10.json) is historical
  pre-publication evidence, not the current adoption status. Preserve it as dated
  provenance rather than silently rewriting its earlier observations.

Advance each existing PR through its established review/integration path, verify
the merged develop bytes, and record actual checkout/session adoption separately.
Do not merge through an unmet owner-review requirement or restart suspended work
as a side effect of documentation acceptance.
