# Operating procedure

Use the pinned [policy 2.0.1](agents/uif-worker-policy.md),
[manifest](agents/uif-worker-policy.json), [environment profile](agents/environment-profiles.json)
and selected repository's current instructions. This describes the required
operating contract: unattended autonomous BAU must continue across quota loss,
Foo/MCP outages and recovery without this conversation. Source acceptance is
separate from installation and useful operating proof; continue the authorized
integration, controlled start and qualification without another approval checkpoint
for that same outcome.

## 1. Reconstruct the current unit and destination

Native Linear is the sole live intake. Resolve immutable workspace/project/issue
UUIDs, current scope/dependencies, execution restrictions and accepted outcomes.
Preserve historical ledger IDs as provenance without starting a ledger selector
or creating a second queue. Reconcile the original operation before retrying an
uncertain submission, completion or publication.

Follow the existing [white-room procedure](white-room/README.md) and use
[tools/white_room/check.py](../tools/white_room/check.py) to compare the selected
project/executor's declared contract with permitted current observations. Reuse
[remote_evidence.py](../tools/white_room/remote_evidence.py) where its exact
[UIF/cloud target and reader contract](white-room/remote-evidence.md) apply.
The default remains one UIF/cloud target; the source ProjectScope extension
requires reviewed repository/ref/project/executor and native Linear UUID bindings.
[transition.WhiteRoomVerifier and CheckpointRead](../tools/white_room/transition.py)
combine that reader with declared comparison and current owner-scoped persistence
at the ownership boundary. Actual authenticated connectors and native/publisher
hook installation remain separate qualification work; source code is not live
ownership proof.

Read current GitHub source, accepted PR/ancestry and Linear dependencies; inventory
surviving work, custody, claims and original receipts. Preserve dirty/local-only
work and use a clean isolated destination workspace without reset/clean. Compare
declared configuration, installation and service bindings with actual destination
state. Foo requires its applicable host/service/data/resource checks; isolated
cloud work uses its own lighter gates, with Foo prerequisites only when needed.
Record passed, drifted, blocked, unknown and unqualified findings precisely.

Match selected persistence to the current issue/source/schema/stage and original
operations. Resume only compatible unaccepted work. Retained checkpoints and
accepted checks are reusable at their exact valid bindings; do not replay accepted
work merely because execution moves. Verify remote checkpoint readback. A missing
checkpoint or vanished session is not verified absence of work or child effects.

The comparator always returns execution_authorized/runtime_readiness_verified
false; its exit code cannot dispatch or start services. Quota restoration is
only one observed prerequisite, never a white-room readiness pass.

## 2. Claim and route through existing controls

Resolve the [per-unit project contract](project-integration.md), lane, actual
executor/user, source/worktree, owned paths, resource budget and reviewer/publisher.
Use the independent off-Foo control authority's supported atomic claim with the current task
generation and coordinator epoch. Verify those bindings before dispatch, shared
integration, Linear transitions and publication. Preserve original operation IDs
and fence a superseded owner before replacement effects.

The authority tracks execution claims, not intake or backlog. Until its runtime
integration is installed and qualified, allocations remain explicitly disjoint
under acknowledged owner coordination. The shared authority and native client
are present in source and tests; their presence does not establish both peers'
installed, authenticated routes or unattended delivery.
Once qualified, Foo/MCP outages leave eligible cloud intake, claims, execution,
review, integration, publication and refill running through that independent
authority and actual project dependencies. Hold only Foo-dependent or unresolved
original effects. Authority loss itself holds dependent claims/effects; preserve
work and automatically resume when current evidence is restored.

Choose available native/cloud commands or deterministic MCP for suitable reads,
builds and checks. Use a Foo model session for useful reasoning/parallelism, with
actual allowance and admission. Prefer economical task-appropriate model/effort,
record exceptions, and distinguish requested from observed settings. Load only
relevant [skills and capabilities](agents/skills-and-plugins.md).

Cloud storage/Git is independent of Foo. MCP user/root transport, deterministic
execution and Codex inference are distinct. Root host access does not authorize
root Git/builds/tests or implicit session control. Discover the actual schema and
workspace through [current Foo guidance](agents/windmill-workspace.md), then bind
the command and original terminal receipt. Never retarget the fixed legacy
wrapper from generic connector availability or invent missing arguments.

## 3. Use the token-mode transition

| Source mode | Required behavior |
| --- | --- |
| `local-ready` | Stokowski owns normal admitted local pickup, execution, review, publication, recovery and refill. The independently durable Morgan lifecycle supervises and recovers configured roles; cloud roles retain independent eligible work. |
| `transfer-pending` | Confirm hard exhaustion or the sustained Foo/MCP failover condition, close unsafe dependent admission, capture available source/dirty-work/claim/checkpoint/operation state and reconcile original effects. The lifecycle ensures a reconstructed, fenced current Morgan epoch. |
| `cloud-active` | After fenced transfer and receiver acknowledgment, Morgan coordinates while project roles continue eligible issue intake through acceptance/refill using the off-Foo authority. Foo/MCP availability is required only by units that actually use it. |
| `local-recovery` | After fresh supported allowance/reachability evidence, applicable white-room checks and a bounded canary, gradually admit independent local issues. Cloud issues keep their owner until completion or reconciled failure. Automatically return to local-ready through supported controls. |

Distinguish allowance exhaustion, authentication errors, transient rate limits,
network failure and tool failure. Reset estimates and unknown quota do not justify
repeated admission. A service's stopped state remains independent of these modes.
The durable lifecycle must operate independently of this conversation and Foo:
schedule or trigger reconciliation, atomically appoint a configured successor
Morgan when needed, fence the old epoch, reconstruct current source/Linear/
LangGraph/original receipts, then acknowledge before effects. Replace executions
of existing project roles without adding roles or repurposing project bindings.
Cooperative handoff alone is insufficient when the predecessor has disappeared.

For Foo/MCP failure use the configurable default 15-minute sustained grace and at
least two qualified probes before an ownership-changing automatic failover. A
healthy qualified probe resets grace; short separated failures do not accumulate.
During grace hold only unsafe dependent admission/effects, inspect the original
operation and continue independent work. Hard quota is a separate confirmed signal
that closes dependent model admission immediately. Use bounded retry/backoff.

If all reasoning capacity is gone, preserve work, continue independent authorized
deterministic operations and automatically resume through the existing approved
routes when fresh evidence permits. Add no provider/account/paid fallback. Actual
off-Foo authority, schedule/trigger, authenticated session control and recovery
observers remain integration/qualification requirements; test source is not their
installation. A user stop/pause is durable and cannot be undone by self-healing.

The local Foo ceiling is 64 Codex sessions, reduced by actual admission and shared
CPU/RAM/disk/I/O/process headroom. MCP jobs and local sessions consume that same
budget. Preserve disjoint writers and relevant project holds, including Foo-only
issues. Increase useful concurrency gradually; a ceiling is not a utilization goal.

## 4. Review, publish and preserve evidence

For supported deterministic checks of a published project branch, follow the
[exact-branch Foo checks](operations/project-checks-source-branch.md) procedure.
The deployed catalog, immutable expected commit and original operation receipt
remain authoritative; the helper never grants publication or runtime authority.

Independently review the exact candidate and required checks under the project's
existing acceptance rules. Identify affected producers/consumers as unaffected,
requiring a current update or unknown with an owner and next check. Keep the sole
integration writer and exact base/head/tree/output bindings. Coding workers cannot
accept their own integration; source integration and product deployment remain
separate outcomes.

Validate the current claim immediately at each supported effect boundary, persist
intent before an effect and read back its destination. After response loss inspect
the original operation and target; do not create a new identity or re-merge source
to repair failed status metadata. Preserve typed milestone/outcome contracts only
for actual native records using them; never fabricate a native execution receipt
for cloud work.

For new bridged UIF → OffMenu publication requests, retain the authenticated
UIF handoff digest, full claim fence and admitted attempt with the original
before publishing. The existing protected control role can POST the exact
`{fence, attempt_id}` to `/v1/publication/fence/read`, which returns only
`{current: boolean}`. Check it at the existing protected consume boundary
before the publication action; a native producer snapshot alone is not the
recipient's current observation. After lost acknowledgement observe that
same original without replay. Keep legacy originals readable and unchanged.
A source implementation does not mount the protected caller or install the
publication bridge.

For a recorded native attempt attestation, the existing control caller can
compare the full expected original request with
`POST /v1/attempt/attest/original`. A match identifies that caller's prior
recorded request and evidence digest. It does not prove the referenced
verdict or effects or revive a stopped or superseded attempt. Use the
independently verified original evidence for settlement; do not write
completion from a model summary or a matching fingerprint alone.


For fresh OffMenu assessments, advance from assessment to investigation only
when all four observations agree on the same original:

1. The report explicitly says the assessment is ready.
2. The coordinator independently verifies the current claim and prerequisites.
3. The exact rendered report is verified as posted under that assessment's
   original operation.
4. The existing UIF control role attests to that same attempt and the admitted
   investigation successor.

A model result or successful process exit does not replace one of these
observations. If any is missing, held or uncertain, hold that attempt and
reconcile its original; do not reset it, post another report or infer approval
from an earlier attempt. Do not apply this rule retroactively to existing work.

Route durable issue decisions, owner changes, source, material checks/review,
blockers and next action to the existing native Linear record. Keep detailed
private receipts/checkpoints in their existing custody. Follow
[memory routing](agents/memory-routing.md); do not create a parallel status store
or copy sensitive project history into shared memory. Report known verified
events promptly and distinguish publication, merge, installation, acknowledgment
and actual useful execution.

## 5. Continue and qualify the controlled start

After each accepted finite unit, continue the next eligible issue within current
scope through the established controls. Reconcile transfers per issue rather than
waiting for every cloud unit or stealing active claims. Accepted work is not replayed.

For this restoration programme, complete the selected ledger-to-native-Linear
reconciliation and demonstrate intake/claims, execution, independent review,
publication, automatic recovery and refill as part of the requested controlled
start and continuous BAU outcome. Complete necessary integration and supported
activation/readback under the current authorization; do not stop for a separate
permission checkpoint or call source publication completion. Preserve specific
project/data holds without making unrelated checks a global foundation gate.
Documentation/source tests establish neither installation nor BAU. Completion
requires observed useful autonomous operation, including absence of this chat,
sustained Foo/MCP outage, coordinator replacement and automatic capacity recovery.
