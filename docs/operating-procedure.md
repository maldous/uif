# Operating procedure

This procedure follows the current [root entrypoint](../AGENTS.md),
[shared worker policy](agents/uif-worker-policy.md) and
[local manifest](agents/uif-worker-policy.json). The selected source checkpoint
uses policy 1.2.3; later work reads the actual local copy rather than treating
this date as a permanent version gate.

## Roles and execution routes

Five project roles own UIF, OffMenu, CIX, ANQR and Circular Quay delivery. Each
uses its own authorized Cloud Git checkout, CPU and storage independent of Foo.
The sixth general Cloud role has no project Git binding. It coordinates
authorized general work without becoming another product or integration writer.

Project owners drive eligible work, dependency coordination and routine
continuation. Use available authorized GitHub interfaces and Foo MCP directly;
routine commands do not require Morgan to relay each operation. Morgan
coordinates Foo-local Codex session orchestration through the session-control
tools actually available to Morgan. Missing native controls are a specific
capability gap, not permission to substitute remote-shell session orchestration.

Cloud reasoning, deterministic MCP execution and Foo Codex inference retain
their distinct identities and prerequisites. Cloud work is not a fallback that
exists only when Foo tokens are exhausted. Add admitted Foo capacity when useful,
available and authorized, preserving current ownership and the shared limits.

## 1. Resolve the unit and exclusive ownership

Use the existing canonical issue or authorized coordination record, including
preserved ledger identities during the intended move to Linear. The normal Foo
harness retains its configured intake and refill controls. Do not silently
migrate history, duplicate another owner's work or replace normal admission.

Reconcile requirement, project, source, current stage, accepted work and original
pending or uncertain operations. Inferred repository work uses its existing
warranted-work/dedup mechanism; a name or issue status is not authority.

Bind the [per-unit profile](project-integration.md). Verify actual executor,
repository/worktree, source, writer and applicable permissions. Preserve active
leases, WIP and recovery custody. A clean suspended lane is not an available
writer. Each product remains self-contained; optional shared orchestration has
requirements only when that lane is selected.

## 2. Execute with a truthful origin and resource scope

Use an isolated task branch/workspace under the established Git flow. Capture
exact commits, trees, owned paths, fixed checks, output hashes and the actual
tool/operation identity. Keep source and runtime payloads in their permitted
custody.

For new and resumed reasoning work, prefer GPT-6.1 Sol Medium or another
appropriate economical choice. Request model and effort where the supported
interface exposes them; use higher capability or effort when warranted and
record the concrete reason. Preserve reliable results and required review.
Requested model/effort and observed resolution are separate facts. Do not claim
an applied model, provider allowance, native session or independent review that
the interface does not establish.

Keep reasoning quota separate from CPU, RAM, storage, I/O and process capacity.
Use actual supported admission, shared resource floors and measured headroom.
A configured ceiling is not a target or proof of safe simultaneous capacity.
Do not create a second scheduler, competing integration writer or invented
resource limit. A blocked route pauses its dependent work while independent
authorized work continues.

For Foo MCP, follow [current workspace guidance](agents/windmill-workspace.md):
use the actual connected `foo` route and discovered schema, with the selected
root script's arguments under `args`. Do not invoke or silently retarget the
fixed legacy wrapper. Retain the admitted operation's original job ID and inspect
that same operation after uncertainty. Transport access is not a new root grant,
credential destination or permission to alter protected state.

Use the actual selected current contract and original historical readers.
Existing reviewed-source support does not automatically accept every temporary
worker output. Qualify only the producer/consumer boundary that the unit really
uses; never fabricate pool leases, completed-native receipts or model facts to
cross it.

## 3. Preserve necessary durable facts

Record issue-specific decisions, owner/scope changes, source commit/tree,
required evidence/integrity references, independent acceptance and continuation
state in the existing coordination record. Use the actual supported action and
sole authorized writer, then read back the destination where an effect occurs.

Do not persist every command, poll or transient progress message in Linear.
MCP/native events and chat provide temporal updates. Report already-known
verified events promptly, then obtain missing or changed details from current
owners. Distinguish prepared, in progress, published, merged, acknowledged and
actually adopted or executed states.

The donor described native-source-milestone and native-source-outcome consumers
with exact structured content. Preserve those markers and bindings for records
that actually use them; generic comments or Done cannot replace their validation.
They are not a requirement to invent a native record for unrelated Cloud work.

## 4. Review and reconcile before effects

Independently review the exact candidate and relevant evidence. Identify affected
producers, consumers and pending inputs as unaffected, current update required
or unknown with an owner and selected check/readback. Unknowns refuse only their
affected scope.

Preserve source, policy, project, issue, owner and original operation bindings,
ordered grants and security checks. Refuse altered evidence, wrong rights or
source, conflicting leases, nonindependent review and uncertain publication.
After a lost response, inspect the original backend operation and destination;
do not replay an uncertain effect under a new identity.

Product source and acceptance remain with their owners. Shared infrastructure
corrections belong to UIF, coordinated with current writers. Active shared
infrastructure filenames and service/runtime bindings must be project-neutral
under the current requirement; their source/deployment migration is separately
owned. A documentation update performs no rename, permission change or adoption.

## 5. Share reusable knowledge without duplicating history

A product record describes its concrete source, checks, review, effects and
limitations. Assess reusable infrastructure lessons against an existing UIF
obligation or warranted new-work producer. Record applicability to profiles,
consumers and pending records with their exclusions and evidence.

Update shared implementation only through the current file owner and reviewed
impact scope. Another project adopts through its own contract and qualification.
Do not copy private product histories into a common memory ledger or create a
new status allocator.

## 6. Continue, transfer or resume within current authority

After an accepted finite unit, the project owner continues the next eligible
work in the authorized scope. Do not close a parent capability for one child.
Use the established harness for normal Foo pickup/refill and Morgan for native
Foo session orchestration, preserving the applicable resource and ownership
controls.

For a transfer, stop temporary admission where authorized, finish or reconcile
in-flight work and transfer ownership exclusively after consumer acknowledgment.
Validate the selected checkpoint and current accepted source/phase; resume only
the first unaccepted stage. Accepted stages are not replayed.

At this dated restoration checkpoint, the current programme's selected
ledger-reconciliation prerequisites precede its BAU resumption. Keep runtime
execution quiesced under existing directions and protected-action holds. Those
conditions apply to this restoration scope; they do not require every future
task to wait for every ledger item or every product. Combined-record delivery retains the
user's relevant-product readiness hold; eligible pure UIF work can continue.

Foundation source delivery does not activate a service or prove BAU. A later
supported transition requires its actual current scope, state, operation
reconciliation and applicable confirmation. After restored BAU, the harness owns
autonomous intake, execution, review, publication, recovery and refill;
supervision observes and reports unless separate engineering is authorized.
