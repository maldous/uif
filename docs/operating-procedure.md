# Operating procedure

Local mode is normal Foo session-based Codex/BAU when tokens are available. MCP mode is the current Morgan/native-agent fallback through Foo MCP. Select the actual mode and origin for the unit; shared Linear identity and evidence continuity do not make their execution receipts interchangeable.

## 1. Resolve work and exclusive ownership

Find the existing canonical Linear leaf and applicable shared UIF obligation. Reconcile requirement, source, current stage, accepted work and original pending/unknown operations. Inferred repository work uses the existing warranted-new-work/dedup mechanism; it is not silently implemented or duplicated.

Bind the selected profile described in project-integration.md. Check actual route/host/user and repository ownership independently from permissions, quota and resources. Preserve active file/task leases and WIP. A clean suspended lane is not an available writer.

## 2. Execute with a truthful origin

Use a bounded isolated workspace/branch and the actual authorized native or normal harness identity. Capture exact commits/trees/paths, output hashes, fixed checks and tool identity, resource/backend receipts and stopped-child evidence as applicable. Preserve private custody. Do not invent native admission, coding sessions, requested/resolved model facts or independent review.

The existing V1 runtime remains the contract authority. Historical records keep their original reader and identity. Fresh current inputs come directly from authoritative requirements and measured state, not converted old prepared records.

## 3. Preserve necessary durable facts in Linear

Persist issue-specific decisions, scope/owner changes, source commit/tree, required evidence/integrity references, independent acceptance and continuation/handoff state. Use the actual consumed action/record format and sole authorized writer, then destination readback and selected-consumer qualification.

Do not persist every command, poll, transient result or progress message in Linear. Use MCP/native events and chat for temporal updates. Activity reporting and durable issue effects are different obligations.

Existing native source milestones and bounded source outcomes require exact structured content. Their markers are native-source-milestone and native-source-outcome; marker-only comments do not qualify. Generic comments or Done do not substitute for validated outcome metadata. Source-only outcome wording must not imply product/runtime acceptance.

## 4. Review and assess impact before effects

Independently review the exact candidate and its measured evidence. Identify actual affected producers, consumers and pending inputs. Classify each as unaffected, mutable current update required or unknown with an owner and selected validator/readback. Unknowns refuse only affected scope; unrelated qualified work can proceed.

Preserve source/policy/project/issue/owner/operation bindings, ordered grants, unknown fields and security checks. Refuse altered evidence, wrong rights/source/project, nonindependent review, conflicting leases, missing child-stop proof and uncertain publication. Reconcile the same original backend operation and destination after a lost response; never replay an uncertain effect under a new name.

## 5. Share reusable knowledge through UIF Linear

A product record describes its concrete outcome, source, checks, review, effects and limitations. Assess reusable infrastructure knowledge against an existing UIF obligation, or the warranted new-work producer when a real gap exists. Record applicability to producers/profiles/consumers, pending records, exclusions and evidence.

Update the shared implementation only through its current file owner and reviewed impact assessment. Record accepted source/evidence and consumer acceptance separately. Update these runbooks and crosslinks; another project adopts only after its own qualification. Do not copy private product histories into a common memory ledger.

## 6. Return to normal execution when authorized

For transfer units, stop temporary admission, finish or reconcile in-flight work, and transfer locks/leases exclusively after consumer acknowledgment. Reopen original checkpoints, validate actual V1 evidence and accepted Linear phase, and resume the first unaccepted stage. Accepted stages are not replayed.

This continuation procedure is defined now; live BAU restoration remains deferred until token usage returns and separately authorized adoption is qualified. Foundation delivery does not depend on that later execution proof.
