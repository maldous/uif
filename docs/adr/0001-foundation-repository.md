# ADR 0001: Separate UIF foundation repository

Status: current scoped foundation decision, clarified 12 November 2026 against
UIF source 8fa48aa56ab1383f7b4df267fbd1da47f7996071.

This clarification uses the retained 6 November foundation source identified in
[the evidence record](../evidence.md). It does not replace the current root
[AGENTS.md](../../AGENTS.md), [README ledger](../../README.md) or
[shared worker policy](../agents/uif-worker-policy.md).

## Context

UIF is the shared physical and virtual infrastructure parent. It is accountable
for Stokowski, Windmill, LangChain/LangGraph, GitHub and Linear integration across
Foo-local and durable Cloud execution. OffMenu, CIX, ANQR and Circular Quay retain
their product source, local contracts and delivery ownership.

UIF must function without requiring product-specific assets. Each product must
be self-contained for its own operation without UIF implementation being
mandatory. Supported optional parent orchestration remains valid when selected.
Historical UIF, USF, TID and OffMenu source names do not select current ownership,
execution authority or a new product dependency.

## Decision

Use maldous/uif for common architecture, methodology, shared implementation
contracts, applicability and references to durable UIF requirements. Use the
actual authorized checkout for its executor; a historical Foo path is not a
prerequisite for a Cloud checkout. The five project Cloud roles and sixth general
Cloud infrastructure role follow the current local policy. The Cloud role owns
only the explicitly assigned maldous/aldous-info-platform repository and remains
outside the five-product delivery matrix. This 16 November amendment supersedes
the earlier unbound-role restriction, without granting provider or publisher access.

UIF owns corrections to the shared parent implementation. Reconcile the current
source writer, rights and consumers before a reviewed adoption or extraction.
Do not copy private product histories, credentials, runtime payloads or datasets
into this repository, or create a competing scheduler, queue, schema or shadow
dispatcher. Preserve exact historical contracts and readers for their original
records. A required current correction uses the existing owner and review flow.

Product records retain their own scope, source, rights and acceptance. Logical
parent governance does not manufacture an unsupported Linear API hierarchy or
authorize moving issue history. Reusable infrastructure lessons flow through
existing UIF obligations with explicit project/profile applicability.

Use bounded task branches and the established Git flow: develop for reviewed
integration and main for accepted releases. Local source, push, merge, deployment,
acknowledgment and runtime adoption are separate facts.

## Consequences

This foundation source unit can be delivered independently of later runtime
proof. The current restoration programme has selected ledger-reconciliation
prerequisites, a runtime pause directive and existing protected-action holds.
Those are dated programme conditions, not a permanent requirement that every
future task wait for every ledger record or every product.

Documentation does not start, repair or qualify a service. Actual autonomous BAU
requires its existing acceptance contract and useful execution evidence.
Unavailable old receipts do not block qualification of the available current
source, select an old operation retry or erase historical scoped acceptance.
