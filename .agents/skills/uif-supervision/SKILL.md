# UIF supervision and durable coordination

## Operating boundary

Morgan is a stable logical coordinator role, independent of this conversation.
The user's conversational controls are start, stop and report; preserve the
requested durable running/stopped state. A report request alone changes no
service state. An explicit user stop/pause cannot be undone by quota recovery,
health probes, coordinator replacement or self-healing.

Under the user's agreed autonomous BAU conditions, the durable lifecycle owns
intake, prioritization within policy, dispatch, execution, independent review,
publication, recovery and refill. It ensures configured Morgan/project executions
and performs routine authorized recovery without needing this chat or another
approval for each step. Conversational supervision observes/reports and resolves
genuine user decisions; it does not create a competing delivery queue or bypass
the harness. Existing project/data holds, access limits and mandatory platform
requirements remain applicable to their actual scope.

Complete currently authorized integration, qualification and controlled operation;
source publication is not the completion checkpoint. Do not stop that same outcome
to seek redundant installation/start permission. Do not interpret this skill or
a report request as new authority for unrelated repairs, accounts, credentials,
paid providers, capacity increases, publication or private data disclosure.

## Selected policy and durable lifecycle

This managed source follows UIF policy 2.0.0. Load the selected environment's
policy/manifest digest, role profile, project instructions and white-room contract.
[Canonical policy](https://github.com/maldous/uif/blob/develop/docs/agents/uif-worker-policy.md)
is a maintenance pointer, not proof of installed bytes or working automation.
Distinguish normative requirements, test source, installed bindings and observed
useful BAU. The off-Foo authority adapter and independent scheduling/session-control
integration remain unimplemented/unqualified until actual source/deployment evidence
establishes them; never claim them from prose or a checker.

The normal contract requires a control authority and durable scheduling/event
trigger independent of Foo/MCP and this conversation. The lifecycle atomically
appoints a configured successor Morgan when qualified liveness/lease evidence
requires it, fences the obsolete coordinator epoch, reconstructs current
Linear/GitHub/LangGraph/original-operation state and acknowledges before effects.
Keep coordinator epoch distinct from per-issue task generations. A vanished chat
or heartbeat does not prove earlier operations stopped. Preserve original IDs
and reconcile uncertain effects; never blindly replay old tool calls.

Retain five project roles (UIF, ANQR, OffMenu, CircularQuay, CIX) plus general
Cloud without a repository binding. Replace failed executions of the same roles
through supported controls; do not repurpose a project or add durable roles.
Project owners continue eligible native Linear issues and their actual
source/review/publication contracts. Linear is sole live intake; the independent
authority holds election/claims, LangGraph holds compatible stage/checkpoint
state, and GitHub records source/merge/publication readback. None substitutes
for another or creates a second work queue.

## Modes and outage continuation

- **local-ready:** Stokowski owns normal admitted local execution/refill. Morgan's
  durable lifecycle supervises, coordinates dependencies and restores failed
  configured roles without manual conversational dispatch.
- **transfer-pending:** close unsafe dependent admission on confirmed quota or
  qualified sustained outage, capture recoverable state and reconcile original
  operations. Ensure a current reconstructed coordinator epoch automatically.
- **cloud-active:** after fenced transfer/acknowledgment, eligible cloud work
  continues through intake, execution, review, integration, publication and refill
  using reachable independent authority and actual project dependencies. A Foo/MCP
  outage blocks only the units/effects that truly require that route or have
  unresolved original outcomes.
- **local-recovery:** fresh allowance/reachability plus applicable white-room
  checks permit a bounded canary and gradual per-issue local re-admission. Current
  cloud units retain ownership until completion or reconciled failure; do not wait
  for all cloud work or steal its units. Quota reset is not a white-room pass.

For Foo/MCP reachability failure, use a configurable default 15-minute sustained
failure grace and at least two qualified probes before ownership-changing
failover. A healthy qualified probe resets grace. During brief glitches inspect
and safely retry the original operation; do not mint duplicate IDs or silently
lose ownership. Hard local quota closes dependent model admission immediately;
authentication, transient rate limits, network and task failures remain distinct.
Use bounded backoff rather than repeatedly entering an exhausted route.

If all inference is unavailable, preserve state, continue independent authorized
deterministic operations and resume automatically through the existing approved
routes when fresh evidence permits. No new provider, paid fallback or spending
is authorized. Foo MCP user/root transport provides host execution, not model
capacity or implicit session control. Repository commands run as the verified
checkout owner even through root transport. Shared host resources constrain
MCP jobs and the 64-local-session ceiling together.

Reuse accepted white-room/source/checkpoint evidence at exact unchanged bindings;
reconstruct the destination and resume only unaccepted stages. Authority outage
holds dependent claims/effects until current ownership is verifiable; maintain
durable recovery evidence and automatically resume safely afterward. Observe
real issue delivery, independent review, destination readback, automatic refill
and recovery with this conversation absent before declaring the outcome complete.

## Establish the target and evidence

Read [references/service-interfaces.md](references/service-interfaces.md) before a service operation or an operational report. Revalidate its documented interfaces against the current authoritative deployment and operations documentation; historical paths and revisions are evidence pointers, not permanent truth.

- Resolve the service instance, environment, project scope, and current owner from verified records. Do not guess a task identity, service unit, endpoint, command, project ID, or repository.
- Treat UIF as a multi-project service. Separate service-wide state from UIF-platform, OffMenu, and CircularQuay delivery. Resolve aliases such as Circular Key through actual project records. A shared infrastructure workspace name does not make every job OffMenu work.
- Prefer read-only connectors, documented status surfaces, and existing authoritative records. Verify that a command advertised as a report does not mutate state before running it.
- Use an already-authorized environment for required host access. Respect missing access and denied actions; do not circumvent them with another tool or account.
- Keep credentials, tokens, raw sensitive datasets, and private message bodies out of commands, reports, and persisted skill content.

## Report

Gather current, time-stamped evidence without changing service or delivery state. Separate:

1. **Control state:** whether the service is running, stopped, paused, draining, or unknown; whether intake/admission is enabled; deployed revision and relevant health evidence.
2. **Real work:** eligible backlog, active coding leases/jobs, actual execution, review, publication, recovery, and subsequent refill, broken down by project where evidence permits.
3. **Exceptions:** exact failed or pending action, owning component or established owner, impact, latest evidence, and any decision needed from the user.

Keep claims no stronger than their evidence. A healthy process is not proof of autonomous delivery. A registered job, sent message, activity label, prepared operator, or successful focused test is not proof of execution, acceptance, installation, publication, or end-to-end success. Reconcile original operation receipts and destination state.

Do not equate no active jobs with no outstanding work. Check whether work is eligible, blocked, queued, admitted, or unavailable to the observer. Report the difference. Do not infer that all projects are processing from evidence for one project, or promise unlimited parallelism: actual concurrency remains bounded by capacity, dependencies, and permissions.

For BAU handover, require observed useful autonomous pickup, execution, review, publication, and refill without Morgan's manual dispatch. Record which parts are demonstrated and which remain unverified. Do not add new delivery gates or hold up already-authorized restoration while collecting evidence.

Give the user a concise result with observation time, material progress, exceptions, and verified links when useful. Mark stale, partial, conflicting, and unknown evidence plainly. Do not fill missing evidence with reassuring guesses or repeat internal activity as progress.

## Conversational start or stop

1. For a conversational start/stop request, confirm it identifies the requested operation and target sufficiently. Reuse existing approval for the same scope; do not ask again solely because executing it requires a tool. Automatic lifecycle recovery instead enforces the existing durable desired state under the agreed conditions above; it needs no new conversational request. Ask only when a genuine target/consequence decision or mandatory platform confirmation remains.
2. Read current control state and outstanding operation receipts first. If the requested state already holds, report that without submitting a duplicate operation.
3. Use only the verified supported control interface for that service and scope. Preserve documented graceful stop/drain behavior and project isolation. If no supported interface is verified or exposed through authorized access, report the exact blocker rather than inventing a shell command or manually reproducing the harness internals.
4. Submit only the requested state transition. Observe its original operation to a terminal result and independently verify the destination state. Distinguish accepted, running, completed, failed, denied, and uncertain outcomes.
5. After a timeout, connection loss, missing receipt, or ambiguous result, inspect the original operation and live state before any retry. Do not launch a duplicate or competing control operation. A denied operation may be retried only when relevant new authorization or evidence permits it and it is known not to have executed.
6. Report the verified outcome and any remaining caveat. If completion is pending, continue observation toward the requested state. If blocked by missing authority, access, or an unsupported control, stop that dependent action and state what is needed.

## Exceptions and automatic recovery

Use read-only diagnosis for conversational reports. The qualified durable lifecycle
performs agreed automatic recovery/self-healing through its existing authority,
resource and review controls; do not require a new prompt for routine continuation.
Outside that scope, identify the exact decision or missing capability rather than
inventing commands, weakening access or launching competing recovery. A worker
recommendation is not additional authority. Preserve existing uncertain operations
and distinguish a completed repair from source preparation or a submitted request.

Treat this skill as workflow guidance, not credentials or installed capabilities.
Follow the user's latest directions and applicable platform requirements. Current
policy requirements supersede dated rollout limits, while historical receipts retain
their original scope and cannot be rewritten as evidence of later installation.
